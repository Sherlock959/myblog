## 为什么是现在

日常工作是建表、写 SQL、配同步任务、盯调度。熟练之后，重复的部分开始变多，真正需要判断的地方变少。

而 AI 数据工程这条线的出现，刚好把数仓工程师的存量能力放大了：

- 知道指标口径是怎么来的；
- 知道表与表之间的血缘；
- 知道数据什么时候不可信。

这三件事，恰恰是大模型问数落地时最缺的东西。模型能写 SQL，但它不知道"订单量"在这个公司里到底指什么。

## 能力地图

我把这条路拆成四层，越往上越接近产品：

| 层 | 内容 | 和数仓的关系 |
| --- | --- | --- |
| 数据层 | 表结构、口径、血缘、质量规则 | 完全复用 |
| 语义层 | 指标定义、维度、同义词、权限 | 数仓工程师的核心优势 |
| 模型层 | Text-to-SQL、RAG、Prompt | 需要新学 |
| 应用层 | Agent、问数产品、评测 | 需要新学 |

真正需要补的是后两层，前两层是存量资产。这个比例比"转行做算法"友好得多。

## 语义层：智能问数的地基

做过一次问数项目就知道，模型生成的 SQL 对不对，八成取决于语义层做得好不好。几个具体做法：

```yaml
# 指标定义（示例）
metric: order_amount
  display_name: 订单金额
  synonyms: [成交额, 销售额, GMV]
  expression: SUM(fact_order.pay_amount)
  default_filters:
    - "fact_order.order_status IN ('PAID', 'SHIPPED', 'DONE')"
  dimensions: [province, city, channel, stat_date]
  owner: 交易域
```

有了这份定义，模型不需要猜"销售额要不要算退款",它只需要选对指标名。

同样的思路也适用于表：

- 表名和源端保持完全一致（大小写也别改），否则模型和人对不上号；
- 每张表必须有注释，字段必须有注释；
- 高频查询路径做成物化视图或宽表，减少模型拼 JOIN 的机会。

## Text-to-SQL 的评测

模型写的 SQL 看着对、结果错，是最危险的情况。所以我习惯先建评测集：

```python
cases = [
    {
        "question": "上个月华东区的订单金额是多少",
        "expected_sql": "...",       # 参考 SQL
        "check": ["行数一致", "金额误差 < 0.1%"],
    },
    # ...
]
```

评测不看 SQL 字符串是否相同，看**结果集是否等价**。字符串相同反而说明模型在背题。

## RAG 与 Agent 的落点

对数据工程来说，RAG 和 Agent 最有价值的地方不是聊天，而是：

- **RAG**：把建表规范、口径文档、同步任务的踩坑记录做成知识库，让新人问"这个字段为什么是 3 倍长度"能直接得到答案；
- **Agent**：把"查表 → 查口径 → 生成 SQL → 跑数 → 解释结果"串成一个可审计的流程，中间每一步都能人工介入。

我现在更愿意把 Agent 理解成"带工具的流程编排"，而不是"更聪明的聊天框"。这和数据平台的调度思维是同一套东西。

## 学习顺序

如果从今天的岗位出发，我会按这个顺序补：

1. **Python**：`pandas` + `requests` 足够起步，重点是能读能改；
2. **LLM API**：先跑通一次流式调用，理解 token、上下文、温度；
3. **Prompt 与结构化输出**：让模型稳定输出 JSON，比让它写诗有用得多；
4. **RAG**：文档切片、向量检索、召回评估，三件套；
5. **Text-to-SQL**：接上自己的库，做一版评测集；
6. **Agent**：工具调用 + 状态管理，落地一个内部小工具。

每一步都以"能交付一个小东西"为终点，而不是以"看完一门课"为终点。

## 小结

数仓工程师转 AI 数据工程，最大的优势不是算法，而是**知道数据什么时候是错的**。

模型不会替你保证口径，口径仍然要由人定义。把语义层做好，把评测集建起来，剩下的模型能力更新换代，你都不用重做。
